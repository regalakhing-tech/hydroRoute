# Database foundation

The SQL migration is local and has not been applied to a Supabase project. Supabase Auth owns credentials, sessions, and identity. A signup trigger and safe backfill create a profile and customer role; editable user metadata is never an authorization source. `private.user_roles` and `private.station_memberships` are provisioned only by trusted operators/backend code. A user with `super_admin` is denied order, customer address, conversation, message and receipt access even if also given a station membership. A rider is denied conversation and message access even if also a customer. Public directory and product visibility requires an approved, active station; products must also be active. New stations default to pending. Registry administrators may inspect pending directory metadata; active station administrators may inspect their own station/catalog metadata.

Customer addresses belong to their creator. An active station administrator can read an address only when an order at that station references it. Orders and their items are visible to the customer and active administrators of the order's station. A conversation is between one customer and station, optionally referencing an order with matching station and customer. Participants may send messages; sender, ID, and time come from the database. Receipts are readable by participants in the same conversation; only their author can insert or refresh them, and refreshes use the database clock. Pickup orders cannot have an address or driver or delivery-only status; delivery requires an address belonging to the customer. Composite foreign keys enforce station and customer consistency.

Catalog prices and item snapshots use integer centavos. Item totals are generated with bigint arithmetic; the order total is the sum of its item totals, not a separately writable column. Clients cannot insert or update orders, items, prices, statuses, memberships or conversations. Trusted order placement code must validate approved active stations and active products, obtain current server-side prices, take product name/price snapshots, insert all items atomically, calculate any fees and the aggregate, and enforce a non-empty basket. No claim is made that this foundation implements checkout, payment, dispatch, status transitions or a delivery algorithm. Likewise trusted code must authorize conversation creation and role provisioning. There are no payment tables or public privileged RPCs.

RLS protects every public table and private authorization tables. Private fixed-search-path definer helpers consult the current Auth UID and are granted only to `authenticated` for policies; clients cannot select or modify private tables. The signup trigger checks its trigger context. Deleting or revoking a role/membership takes effect in database checks rather than waiting for JWT metadata refresh. Review deletion, retention, audit, rate limiting, operational role administration, and policies for production before deployment.

## Verified approval and access cases

The migration uses registration_status with pending as the default. Anonymous station/product policies require approved status and active state. No authenticated client has station approval privileges. Station/order/conversation creation remains a trusted backend operation that must validate the approval state before creating new business records.

The local PostgreSQL suite uses real SET ROLE checks for approved, pending, suspended and inactive directory records; both sides of a two-station/customer setup; inactive and revoked memberships; Super Admin with customer and station-admin roles plus active membership and owned records; rider-owned threads; cross-conversation receipts; sender/time/role/price forgery; independent composite foreign keys; and valid and invalid pickup orders.

Pickup uses the database status collected for the UI label Picked up. Profile display names currently expose only the caller's own profile, so future live inbox integration must provide an authorized lookup of participant display names. No hosted Auth, Google OAuth, Data API, Realtime or migration-deployment integration has been performed.
